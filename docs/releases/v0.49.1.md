# WordWise v0.49.1 —— 窗口收起 / 最小化时也要出声

> 这是 v0.49.0 的一个**定点修复版**，只动发音链路，其它功能不变。
> v0.49.0 的改动见 `docs/releases/v0.49.0.md`。

---

## 问题

窗口**最小化**或**收进托盘**（设置 → 记忆辅助内容，默认开「关闭窗口时缩小到托盘」）
之后，点朗读 / 答完题自动发音：**没有声音，也没有任何报错**。

---

## 根因（四条，按因果顺序）

| # | 根因 | 具体位置 |
| --- | --- | --- |
| 1 | **AudioContext 被挂起后「假成功」** | `ctxFor()` 里写的是 `if (ac.state === 'suspended') ac.resume();` —— `resume()` 返回 Promise 却被**丢弃**，紧接着就 `decodeAudioData + src.start()`。上下文还挂着时 `start()` **不报错也不出声**，而 `playViaWebAudio` 在 `start()` 之后立刻 `resolve(true)`：上层以为播成功了，既不降级也不提示 |
| 2 | **完全没有可见性处理** | 修改前全项目 **0 处** `document.hidden` / `visibilitychange`。窗口最小化/收起后页面进入 hidden，Chromium 会挂起该页面的 AudioContext 并节流定时器；回到前台没有任何恢复动作，隐藏期间发起的朗读直接蒸发 |
| 3 | **后台定时器被节流，把状态锁死** | 收尾用的 `setTimeout(finish, tail)` 与 `<audio>` 的 3 秒挂起判定，在隐藏页面被 Chromium 钳制（≥1 秒，长时间隐藏后 1 分钟一次）→ `speaking` 长时间为真 → 之后每次点朗读都被当成「正在播」而走停止分支 → 点了没声音 |
| 4 | **隐藏态下没有一条不依赖页面的通路** | WebAudio 被挂起、`<audio>` 受自动播放策略与后台节流限制；而本机实测 `<audio>` 管线本就整体失灵（连 188 字节标准 PCM 都挂起），两条页面内通路在隐藏态下同时不可用 |

---

## 修法

### 1. 主通路：先确认上下文真的在跑，再开播

`speak.js` 新增 `resumeCtx(ac)`：**await** `resume()`（500ms 上限），返回是否 running；
`playViaWebAudio` 先 `resumeCtx` 再解码开播，并在 `src.start()` 之后**复核**
`ac.state === 'running'` —— 不是 running 就按失败处理，交给下一条通路。
（隐藏页面上 `start()` 照样「成功」，只有看状态才分得清真响没响。）

### 2. 新增原生播放通路（后端）

`cmd_tts_play_native`：把 WAV 字节交给**系统**播放（Windows 下由 Rust 直接调 winmm
的 `PlaySoundW`，零新增依赖）。它由后端直接把音频送给系统音频接口，与页面可见性、
自动播放策略、后台节流**统统无关**，是隐藏态下唯一稳的一条路。
配套 `cmd_tts_stop_native`：窗口里点停止，藏起来的那条原生播放也跟着停。

### 3. 通路顺序：按可见性选择

| 状态 | 顺序 |
| --- | --- |
| 窗口可见 | WebAudio（按文件原生采样率，音质最好）→ `<audio>` → 原生 |
| **窗口隐藏/最小化** | **原生**（先）→ WebAudio → `<audio>` |

### 4. 可见性恢复 + 状态自愈 + 补播

- `visibilitychange` 回到前台：把所有缓存的 AudioContext 拉回 running；
- 隐藏期间被吞掉的那一次朗读会记下来，回前台 120ms 后**补播一次**（超过 30 秒就作废，
  免得隔半天突然响一声）；
- `speak()` 入口按「有没有真的活动源」复位 `speaking`，不再依赖被节流的定时器。
