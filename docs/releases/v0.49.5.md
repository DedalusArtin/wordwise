# WordWise v0.49.5 —— 修「点了喇叭一声不出」：语言错标才是真凶

> 紧接 v0.49.4 的 hotfix。**只改语言判定链路**，不动变形栏与查询历史。
>
> 用户报了三个现象：点喇叭没反应、日语模式点过一次之后就一直念不出来、
> 其它语言的适配普遍一般。三个现象其实是**同一个根因**。

---

## 一、先说结论：不是语音模块的错

查了实机数据库 `wordwise.db`，结果是：

```
词条语言分布：  ja 9,888    en 20
其中 lang='ja' 但词形是纯拉丁字母：5,057 条
样例：April  Bible  Catholic  Christ  Easter  Latin  March
      Marxist  Monday  Thanksgiving  X-ray  abandon  abdomen
```

词库归属一看就明白：

| 词库 | 声明语言 | 词条数 |
| --- | --- | --- |
| `kaoyan-core`（考研核心词汇 —— **英语**） | `ja` ❌ | 5,057（**全部是拉丁字母**） |
| `jlpt-n1` / `jlpt-n2`（日语） | `ja` ✅ | 3,070 / 1,778（真·假名汉字） |

**整本考研英语词表被标成了日语。** `accord`、`abandon`、`Monday` 全是。

于是朗读的时候：

```
lang = "ja"  →  去找日语 piper 语音包  →  本机装的是 en_US-amy / zh_CN-huayan，没有日语
             →  回退系统语音，tag = "ja-JP"
             →  中文 Windows 多半没有日语语音
             →  WebView 拿到一个匹配不上任何声音的 lang  →  一声不出
```

用户看到的就是「点了喇叭完全没反应」。而且它**不报错、不弹提示** ——
静默失败最难排查，用户只能得出「软件坏了」的结论。

同一条错数据还会连累：查词走日语分支、AI 讲解按日语组织、释义语言、
音标标成「读音」而不是「英/美」。这就是「其它语言适配一般」的同一根因。

---

## 二、为什么启动清理一直没修掉它

项目里**早就有**语言清理（`purge_lang_mismatch`，启动时自动跑，维护面板
也能手动触发）。它一条都没修，因为判定函数自己放行了：

```rust
// 改前 —— src-tauri/src/lang.rs
pub fn lang_compatible(word: &str, lang: &str) -> bool {
    match script_of(word) {
        Script::Kana     => lang == "ja",
        Script::Hangul   => lang == "ko",
        Script::Han      => lang == "zh" || lang == "ja",
        Script::Cyrillic => lang == "ru",
        …
        Script::Latin | Script::Other => true,   // ← 拉丁字母一律放行
    }
}
```

注释里写着的理由是「日语词库里有罗马字外来语，判严了会误杀真实数据」。
这个顾虑本身没错，但代价算错了：

- 放行 → 5,057 个英语词念不出声，**静默失败**；
- 收紧 → 几个罗马字条目被归到 `en`，**看得见、可手工改**。

更要命的是第二处 —— 就算闸门判了「不自洽」，决议函数又把语言决议回原值：

```rust
// 改前
Script::Latin | Script::Other => req.unwrap_or(fallback),  // req = "ja" → 还是 "ja"
```

**`lang_compatible` 说有问题，`resolve_lang` 说没问题**，两个函数互相抵消，
清理逻辑得到一个「want == 现状」的目标，于是一行都搬不动。5,057 条就这么
一直烂在库里 —— 这就是「日语模式点了一次，之后一直念不出来」的完整机制。

---

## 三、改法

### 1. 闸门收紧：拉丁字母只能配拉丁语系

```rust
// 改后
Script::Latin | Script::Other => !is_non_latin_lang(&lang),
```

`is_non_latin_lang` 判的是中日韩俄阿拉伯希伯来泰希腊这些**非拉丁语系**。
英 / 法 / 德 / 西之间字形上分不出来，这里**不越界去判**，仍然交给调用方意图。

### 2. 决议同向：拉丁词不可能被决议成非拉丁语言

```rust
// 改后
Script::Latin | Script::Other => match req {
    Some(r) if !is_non_latin_lang(r) => r,
    _ if !is_non_latin_lang(fallback) => fallback,
    _ => "en",
},
```

两条合起来，启动清理才会真正开始搬这 5,057 条。

### 3. 顺手堵住「再次发生」的两个入口

只修存量不够 —— 只要还能再写进去，下次重启前照样是坏的。

| 入口 | 改法 |
| --- | --- |
| `cmd_import_words`（批量导入） | **逐词决议**而不是整批共用一个 `lang`。原来「不合 `lang` 就过滤」，闸门收紧后这一批英语词会**一个都导不进来** —— 同样不能用 |
| `importer::build_entry`（词库导入） | `e.lang` 不再照抄调用方，改走 `resolve_lang(word, Some(lang), lang)` |

`cmd_add_word` 本来就先 `resolve_lang` 再过闸门，这次自动跟着修好了。

## 四、迁移动作与安全性

启动时三步依次跑（`src-tauri/src/state.rs`）：

1. `fix_builtin_book_langs` —— 把 `kaoyan-core` 从 `ja` 改回 `en`（权威目录里它就是 `en`）；
2. `purge_lang_mismatch` —— 按新规则把 5,057 条从 `ja` 搬到 `en`；
3. `repair_entry_json_langs` —— 对齐 `entry_json` 里的 `lang`。

搬动是**整行迁移**不是 `UPDATE`：三张表的 `lang` 都在主键里，直接 UPDATE
会在「目标语言下已有同名行」时撞主键。进度用 `INSERT OR IGNORE` 跟着搬，
且**旧行只在目标行确实存在时才删** —— 学习记录绝不会丢。

`study_state` 目前只有 22 行（都在 `en`），所以本次实际不会动到进度。

## 五、副作用（说清楚，不含糊）

日语词库里若真有**罗马字注音**条目（「アイスクリーム」的 `aisukuriimu`），
会被判成 `en`。这是两害相权取其轻，且是可逆、可见的。

## 验证

- Rust 单测 **352 / 352**（新增 2 条）；
- 前端冒烟 223 条全部通过；
- 实机数据核对：`ja` 9,888 → 其中纯拉丁 5,057 条待迁移，与 `kaoyan-core` 的 5,057 条完全对应，两组集合**不相交**（jlpt 库里没有拉丁词），迁移不会误伤日语词。

## 手动验证步骤

1. **先彻底退出再重开**（迁移只在启动时跑，开着窗口不生效）。
2. 设置 → 数据库维护 → 语种统计：应看到 `en` 约 5,077、`ja` 约 4,831。
3. 查 `accord` → 点词头喇叭，应**立刻出声**（美式英语）。
4. 随便点一个考研词表里的词（如 `abandon`）→ 音标应标「英 / 美」而不是「读音」。
5. 查一个真日语词（如 `たべる`）→ 仍走日语分支，不受影响。
6. 日语模式下再导入一批英语词 → 应正常导入，且落库为 `en`（不再重演）。
