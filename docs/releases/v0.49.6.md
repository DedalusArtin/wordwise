## 一、显存只涨不降（前半）

### 现象与实测

用户截图显示显存 `10,159 / 12,282 MiB`，但 GPU 利用率只有 **28–33%** ——
这是「**占着不放**」，不是「在算」。

先说明一个容易走错的方向：`nvtop` 和 `nvidia-smi --query-compute-apps` 在
**Windows 上拿不到每进程显存**（WDDM 的限制，全显示 `N/A`）。所以光看那两个
工具的每进程列，**什么都证明不了**，只能靠进程名逐个排查。

排查结果：

```
Get-Process llama-server  →  4 个进程

PID     启动时间    父进程     状态
22488   13:09      32684      父已退出 → 孤儿
15268   15:29      35516      父已退出 → 孤儿
27836   15:55      15792      父已退出 → 孤儿
21048   16:55      40460      父已退出 → 孤儿
```

四个进程**命令行完全相同**，都在加载同一个
`WDATA\models\Qwen3-1.7B-Q4_K_M.gguf`，而且父进程**全部已经退出**。

杀掉这 4 个之后：

```
清理前：10,221 MiB 占用
清理后： 3,650 MiB 占用   →  释放约 6.4 GB
```

## 二、根因：`stop_server` 只认识「自己记着的那一个」

托管服务在内存里就是一个 `Mutex<Option<ServerHandle>>`：

```rust
static SERVER: Mutex<Option<ServerHandle>> = …;
```

`stop_server()` 只能杀掉**本进程记着的那个 handle**。如果上一轮 WordWise 是被
**崩溃 / 任务管理器强杀 / 断电**结束的，它根本没机会跑清理，那个 `llama-server`
就成了**孤儿** —— 而新启动的 WordWise 对它**一无所知**。

于是：**每重启一次，就多攒一个常驻显存的后台服务**。用户实机 4 小时里攒了 4 个。

这跟「软件显存回收能力弱」不完全是一回事 —— 是**根本没去找**那些不属于自己的进程。

## 三、改法：以系统进程表为准，而不是以内存记录为准

### 1. 先拿到「所有托管进程」

```rust
fn managed_pids() -> Vec<u32>
// Windows: tasklist /FI "IMAGENAME eq llama-server.exe" /FO CSV /NH
// Unix:    pgrep -f llama-server
```

### 2. 一次抓全系统的 `pid -> ppid`

关键点：**只抓一次**。

```rust
fn process_table() -> Option<HashMap<u32, u32>>
// Windows: Get-CimInstance Win32_Process → 逐行吐 "pid,ppid"
// Unix:    ps -e -o pid=,ppid=
```

第一版是「每个候选 pid 起一个 PowerShell 去问父进程在不在」。问题有两个：

- 一个 PowerShell 冷启 300–600 ms，N 个进程就是 **N 次串行等待**，
  启动路径上白白卡一两秒；
- 把「CIM 查询权限」这种事**重复做了 N 遍**，在受限上下文里更容易失败。

改成一次性全表扫描后，**成本与进程数无关**，Rust 侧做集合运算即可。

### 3. 判据：父进程还在不在

```rust
fn orphans_from_table(table: &HashMap<u32, u32>, pids: &[u32]) -> Vec<u32>
```

三条全中才算孤儿：

1. `pid` 要在表里 —— 已经退出的进程不占资源，不用我们动手；
2. `ppid` 不能是 `0` 或自身 —— 内核/根进程，判不了 → **按有主处理**；
3. `ppid` 不能出现在表里 —— 父进程还在 → **有主 → 别碰**。

这条判据比「是不是我们起的」更准，因为它同时能正确处理两种情况：

| 情况 | 父进程状态 | 处理 |
| --- | --- | --- |
| **用户多开**（两份 WordWise / 开发时开着调试实例） | 活着 | **不动** —— 杀了就是砸别人的饭碗 |
| **崩溃残留** | 已退出 | **收** —— 原主人走了，显存却一直占着 |

### 4. 挂到三个位置

| 位置 | 作用 |
| --- | --- |
| `start_server`（**起新进程之前**） | 先 `stop_server()` + `sweep_orphans()`；扫掉了就等 600 ms 让驱动回收显存，避免「旧的没释放、新的又要分配」而失败 |
| `shutdown()` | 退出时 `stop_server()` + `sweep_orphans()` |
| `spawn_autostart` | **不管 `auto_start_local_llm` 开没开**都要扫一遍 —— 用户不开自动启动 ≠ 允许残留进程常驻 |

## 四、实测验证（不杀活进程）

关键验证：本机当时正跑着一个**用户手动启动**的 `llama-server`（PID 27052），
它的父进程是存活的 `wordwise`（PID 41700）。探针必须判它**有主、不杀**：

```
进程表条目数: 430
llama-server PIDs: 27052
  PID 27052 -> OWNED parent=41700     ← 正确：父进程还在，不动
```

这是「不误伤多开实例」的正向证据。

## 五、朗读：补希腊语，并把「静默失败」改成能看懂的提示（后半）

用户说「其他语言的适配没这么好…包括朗读」。实测后发现问题不在我们的代码逻辑，
而在**随包引擎版本**上 —— 这是一个硬约束，先说清楚。

### 1. 对照实验（同一个引擎，只换语音包）

| 语音包 | 结果 |
| --- | --- |
| `en_US-amy-medium`（英文） | ✅ 退出码 0，正常出 wav |
| `el_GR-joy-medium`（希腊语） | ✅ 退出码 0，正常出 wav |
| `ko_KR-kss-medium`（韩语） | ❌ `"aɪ" is not a single codepoint (ids=161,)` |
| `ja_JP-hi_fi_captain-medium`（日语） | ❌ **退出码 2，stderr 全空** |

### 2. 判据：语音包的音素表里有没有「多码点音素」

| 语种 | `phoneme_type` | 多码点音素 | 随包引擎 |
| --- | --- | --- | --- |
| 希腊 `el_GR` | `espeak` | **0** | ✅ |
| 中文 / 俄语 / 德法西意葡 | `espeak` | 0 | ✅（已在清单） |
| 韩语 `ko_KR` | `espeak` | 5（`aɪ aʊ ɔɪ eɪ oʊ`） | ❌ |
| 希伯来 `he_IL` | `hebrew` | 5 | ❌ |
| 泰语 `th_TH` | `thai` | 5 | ❌ |
| 日语 `ja_JP` | **`japanese`**（openJTalk） | —— | ❌ |

`piper.exe --help` 里**只有** `--espeak_data`，**没有** openJTalk 相关参数 ——
所以 `phoneme_type: japanese` 的语音包根本派发不出去，直接静默退出。

### 3. 为什么不能简单「换个新引擎」

- `rhasspy/piper` **已归档**（11.3k stars，archived=true），
  最后发布 **2023.11.14-2** —— 就是我们随包的 1.2.0 那一代，**上游不会再有新 exe**。
- 后继项目 `OHF-Voice/piper1-gpl` 仍在维护（最新 v1.8.0，2026-09），
  但**只发 Python wheel**（`piper_tts-1.8.0-cp39-abi3-win_amd64.whl`，34 MB），
  **没有独立 Windows exe** —— 要用就得把 Python 运行时一起打进去，属于架构级改动。

所以本轮的选择是：**在这个约束下，把「能用的」补上、把「不能用的」说清楚**。

### 4. 本次改动

**① 新增希腊语语音 `el_GR-joy-medium`**

它是唯一一个实测能在随包引擎上跑通、但清单里**没有**的非拉丁语种。
端到端验证：退出码 0、正常产出 wav（37,024 B）。

**② 修「静默失败」——这是更要紧的一条**

原来 `synth_blocking` 把引擎的 stderr 直接拼进错误信息。遇到日语那种
**退出码 2、stderr 为空**的情况，前端收到的是：

```
语音合成失败：          ← 冒号后面一片空白
```

用户看到的还是「点了没反应」，等于什么都没说。现在改成：

```
语音合成失败：语音引擎无输出即退出（退出码 2）。多半是这个语音包要求的音素格式
比随包引擎（piper 1.2.0）新，例如日语/韩语语音。请改用系统语音，或换一个本应用
清单里标注可用的语音包
```

**③ 补齐语种名映射**：后端 `translate::LANGS` 加 `el`（希腊语），
前端 `ui.js` 的 `langLabel` 补 `el` / `th` / `he`。

### 5. 新增 3 条测试守卫

| 测试 | 钉住的规则 |
| --- | --- |
| `catalogue_excludes_engine_incompatible_voices` | 已知跑不通的语音（日语/韩语/泰语/希伯来语…）**不许进清单** —— 将来有人「顺手加个日语」会先被拦下 |
| `greek_is_the_only_non_latin_addition_and_it_is_listed` | 希腊语必须在清单里，且体积/地区码正确 |
| `silent_engine_exit_produces_actionable_message` | 引擎静默退出时，错误信息**不能是空的**，必须给出下一步 |

- **日语 / 韩语离线朗读仍然没有**。原因见第五节：随包引擎 1.2.0 处理不了它们的
  音素格式，而上游已归档、后继项目只发 Python wheel。这一版的做法是
  **如实告知 + 回退系统语音**，而不是塞一个「下得下来、读不出声」的包进来。
  要真正支持，需要换引擎（打包 piper1-gpl + Python 运行时），属于后续独立工作。

  且未开开发者模式，`cargo-mobile2` 建符号链接失败。Windows 安装包与便携版不受影响。
- `git push` 有提交仍留在本地（网络反复 reset，不影响使用）。
